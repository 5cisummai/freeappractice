Executive summary

What changed

Correctness first

Atomic leases, idempotent attempts, conflict-safe upserts, validated AI payloads, and bounded request bodies remove the highest-risk failure modes.

Queries shaped to use

History, dashboard, bookmarks, profiles, referrals, FRQs, and admin reads now fetch the data each screen or operation actually needs.

Fewer hidden conventions

The schema is split by domain, public layout is shared, request plumbing is reused, and the repository map now tells humans and agents where behavior belongs.

Critical pre-refactor fixes

Correctness risks closed

Projected profile writes

Replaced broad replacement writes with explicit operations and regression coverage, preventing omitted fields from being erased.

Quality cost aggregation

Replaced unsupported compatibility aggregation with explicit SQL and tests.

Quality lease races

Claiming and lifecycle transitions now use atomic compare-and-set semantics with concurrency tests and audit validation.

Insight report persistence

Nested report PDF updates use direct JSONB mutation; unknown generic-adapter fields fail loudly instead of disappearing.

Retry-safe attempts

The client supplies an attempt UUID and one CTE conditionally records the attempt, progress, and referral activation exactly once.

Conflict-safe canonical records

Question, FRQ parent/child, plan, and compatibility upserts now update deterministically after uniqueness races.

Remaining debt

What not to over-refactor next

Priority Residual issue Recommended next move
P2 Several domain models still use the generic compatibility adapter. Replace a compatibility call only when its owning feature is next changed; do not create a second repository framework.
P2 Some client bundles exceed 500 KB. Measure route chunks, then lazy-load the heaviest editor/chart/PDF feature. Keep this evidence-driven.
P2 Subject membership is represented in both profile data and relational subject rows during migration. Backfill, verify, then remove the legacy column in a dedicated reversible migration.
P3 A few cohesive but large files remain, notably Insights, Coach, settings, changelog, and question-quality service. Split only when a concrete change reveals a stable submodule; line count alone is not an architecture.
P3 Build output includes optional-dependency notices. Document accepted warnings or remove unused optional integrations when product scope confirms they are unnecessary.

No unresolved P0 or P1 findings remain from this review.

Operating rules

Keep the codebase simple

  1. Put validation and authorization at the route or layout boundary.
  2. Name domain functions after the operation they perform, and return only the shape the caller needs.
  3. Use one SQL statement or transaction for invariants that must change together.
  4. Bound every user-controlled body and every list read used by a serverless request.
  5. Prefer a direct function over a new abstraction until there are at least two real, stable consumers.
  6. Do not add capabilities to the generic Neon compatibility adapter.
  7. Pair every concurrency or retry fix with a regression test that reproduces the failure mode.
