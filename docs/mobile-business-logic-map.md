# Web and mobile business-logic map

Updated November 3, 2026 after the shared-function refactor. Includes current workspace changes.

## Basic pattern

```text
Web loader/action -> exported business function -> Drizzle
Mobile app -> API wrapper -> same business function -> Drizzle
```

Business functions own resource permissions, rules, and data operations. Wrappers establish identity, parse input, and handle HTTP/form responses, cookies, redirects, streaming, and request analytics. Keep functions in existing domain folders; do not add service classes, repository layers, or a generic framework. Small single-use presentation and request parsing stay inline.

**Shared** means core operations delegate to library functions. **Mixed** means some app-level composition remains in the wrapper. **Adapter** means intentional transport/framework/operational handling, not a required refactor. These classifications describe static server code, not verified native-client parity.

## Remaining boundaries

- The app layout still composes navigation capabilities, onboarding redirects, organization selection, and beta prompts. Some data is available through home/settings/profile/auth APIs, but there is no equivalent single bootstrap endpoint. Web-only redirects and navigation decisions can stay in the layout; add a bootstrap response only if the native client needs it.
- The home wrappers intentionally shape different responses and still compose shared access/study-plan reads. No generic dashboard abstraction is necessary.
- Auth, streaming, feedback/bug-report HTTP handlers, cron, and webhook adapters remain transport-specific. Shared engines and persistence already exist beneath many of them. Do not extract purely to meet a file-size or naming target.
- Public blog/SEO reads have no dedicated mobile JSON API. Expose them only when mobile needs them.
