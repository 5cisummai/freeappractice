# Security & Privacy

## Scope

This is an internal engineering reference based on the repository state reviewed on 2026-08-15. It covers the SvelteKit application, Neon/Drizzle schema, authentication, API routes, client telemetry, AI and memory integrations, and checked-in configuration. It is not a legal certification, penetration test, provider configuration review, or statement of FERPA, COPPA, or other regulatory compliance.

The code establishes application behavior. Provider contracts, console settings, access-control lists, production secrets, backups, incident procedures, and operational retention need separate verification.

## Current Architecture

The application is a Vercel-hosted SvelteKit service. Server routes use Better Auth with a Neon PostgreSQL Drizzle adapter. The database holds authentication records in the `auth` schema and product data in `app`; foreign keys generally cascade from `auth.users`.

Authenticated practice, tutor, Coach, and Super endpoints obtain identity from a Better Auth same-origin session cookie. Super data is processed in Neon and, when enabled, in Mem0 OSS backed by OpenAI embeddings/LLM calls and Upstash Vector. Redis/Upstash supports short-lived rate limits, locks, approvals, usage reservations, and idempotency. OpenAI-compatible calls produce questions, grades, tutor responses, Coach responses, titles, and study plans. Optional billing uses Stripe, and transactional mail uses Resend.

## Data Flow

### Account creation and authentication

Better Auth creates an `auth.users` row, then its create hook creates `app.user_profiles` (`src/lib/auth/server.ts`). Email/password sign-up and the Google signup button require a 13+ checkbox. Checking it writes a short-lived, first-party `fap_age_attestation` cookie (`src/lib/auth/age-attestation.ts`); Better Auth's `user.create.before` hook rejects new account creation when that cookie is absent (`src/lib/auth/server.ts`). Google One Tap is not offered on `/signup`, so it cannot bypass that UI gate, although One Tap on other public routes still relies on the server-side cookie gate for new accounts. This is self-attestation, not age assurance. Email/password sign-up requires email verification, hashes passwords with bcrypt cost 12, uses 15-minute reset and email-verification tokens, and revokes sessions on password reset. Google sign-in is conditional on configured credentials. Session records include IP address and user agent (`src/lib/server/neon/schema/auth.ts`).

After authentication, users without a durable `ageConfirmedAt` value are redirected to `/app/confirm-age` before account surfaces and protected account APIs. This post-auth gate protects existing or previously created accounts, but it is not a pre-collection age check.

### Practice activity

Authenticated practice APIs write user-keyed MCQ/quiz/FRQ rows in Neon. The app reads those records for progress, history, Coach, and optional personalization. A Settings action calls `clearPracticeDataForUser`, which removes attempts, progress, bookmarks, and FRQ attempts but retains the account and other data (`src/lib/users/clear-practice-data.server.ts`).

### AI tutor and Coach

The standard tutor sends the current question, answer/explanation, supplied conversation history, and user message to the configured OpenAI-compatible endpoint (`src/lib/tutor/service.server.ts`). FRQ tutoring additionally sends the prompt/materials, student responses, and grading feedback. Super adds server-derived profile preferences, progress, recent FRQ performance, relevant memories, and durable conversation history. Super conversation messages are stored in Neon before and after streaming (`src/lib/super/agent-stream.server.ts`).

### Tutor memory and personalization

After a user has age-confirmed, has Super access, enables memory, and acknowledges the disclosure, Mem0 receives up to 2,000 characters each from a user and assistant exchange. The code instructs Mem0 not to retain identity/contact/school/location/age/health/family/financial information or transcripts (`src/lib/mem0/service.server.ts`), but this is a prompt-level control rather than deterministic content filtering. Memories are keyed by a random per-user `mem0UserId`, filtered by that identifier, and stored in an environment-specific Upstash Vector namespace.

### Analytics, monitoring, billing, and mail

PostHog client capture is consent-gated except that rejected consent permits cookieless page-view measurement. The consent banner tells under-13 visitors to reject optional analytics and not create an account; rejecting analytics is not an age check or permission to use the service. The server sends consent-gated user-related events and always sends narrowly defined anonymous operational metrics. Vercel Analytics/Speed Insights and Sentry initialize in production. Stripe receives billing data only when configured and used; Resend receives recipient email and transactional message content. See the subprocessors table for limits of what code can establish.

### Account deletion

Better Auth requires deletion confirmation where applicable. Before deletion, the app cancels Stripe subscriptions and creates a durable cleanup job. After deletion, it removes app-owned Neon data and schedules Redis, PostHog, and Mem0 cleanup (`src/lib/auth/server.ts`, `src/lib/super/account-cleanup.server.ts`). Cascades remove account-owned rows such as sessions, conversations, messages, and most practice rows. Mem0 cleanup retries through the scheduled maintenance route after failures. The PostHog deletion call needs dedicated provider credentials; without them it fails the cleanup job and requires operational remediation. No code was found to erase Sentry/Vercel logs, Resend mail, Stripe records, provider-side OpenAI inputs, or backups.

### Encryption verification

A provider statement that only says “encrypted” or “HTTPS” is not enough to confirm the requested strength. Where the application allows a compatible or customer-selected endpoint, the provider claim applies only to the endpoint actually configured in production.

## AI Data Handling

OpenAI-compatible calls are centralized in `src/lib/ai/service.server.ts`, with a base URL configurable through `OPENAI_BASE_URL`. Major paths are tutor (`src/lib/tutor/service.server.ts`), Super Coach (`src/lib/super/coach.server.ts`), conversation titles, question generation, question-quality review, and Mem0 extraction/embedding.

Confirmed minimization controls include server-owned question/grade context, bounded message lengths, a random Mem0 user identifier, memory opt-in/disclosure, `disableHistory: true` in the Mem0 client, and instructions to treat student/memory text as untrusted. The code does not configure OpenAI provider retention, training, zero-data-retention, or regional processing. It also does not apply deterministic PII redaction before transmitting free text. Those are the primary gaps to resolve before handling school records or sensitive student content.

Recommended changes: add clear student-facing “do not include personal information” guidance at each AI input; redact common identifiers where feasible; use provider accounts/settings that contractually restrict retention/training; maintain a model/data-flow inventory; and create a school-mode control that disables external AI until approved terms are in place.

## Analytics & Telemetry

- PostHog initializes in production with `capture_exceptions: true`, masked inputs, selected text masking, and network-query redaction. Consent is stored in localStorage and a one-year cookie. Detailed capture and identify events are sent only after consent; pending or rejected consent allows cookieless `$pageview` / `$pageleave` only (via `cookieless_mode: 'on_reject'`). Replay settings, IP/geolocation handling, project retention, and provider access must be checked in the PostHog console — cookieless events also require Cookieless server hash mode enabled in the PostHog project.
- Server PostHog events require the consent cookie except `captureAnonymousServerMetric`, which intentionally uses a shared `server` distinct ID and documented non-PII properties. Review future call sites to preserve that invariant.
- Sentry initializes with `tracesSampleRate: 1` and `enableLogs: true` in production. No `beforeSend` scrubber or trace-sampling reduction is configured in the reviewed code. This increases the importance of checking Sentry SDK defaults, server request capture, retention, and alerts.
- Vercel Analytics and Speed Insights load for all browsers. The repository does not establish the production project’s collection, retention, or access settings.
- Application logging applies key/value redaction and bounds output in `src/lib/server/logger.ts`; it redacts common credential, ID, email, IP, prompt, message, and content fields. Error stacks may still contain sensitive context, so provider/log configuration and error construction require operational review.

## Authentication & Authorization

Confirmed controls:

- Better Auth uses server-side, same-origin session cookies; email/password accounts require verified email; password hashing is bcrypt cost 12; reset tokens expire in 15 minutes; reset revokes sessions.
- OAuth tokens are configured for encryption, account linking trusts only Google, and a locally linked account must have a verified email.
- New account creation has a server-side age-attestation cookie gate. The email/Google signup UI requires the same 13+ checkbox, and Google One Tap is not offered on `/signup`.
- Auth endpoints have database-backed rate limits, and several AI/bug-report/shared-set endpoints apply Upstash rate limits.
- `hooks.server.ts` sets HSTS, `X-Frame-Options`, `nosniff`, strict referrer policy, permissions policy, a CSP, API no-store headers, and an allowlisted CORS response. Cron routes use a timing-safe bearer-secret comparison.
- Reviewed object routes use user ownership predicates, including conversations and memory opaque-ID resolution. Admin pages/routes require a session and an ID in `BETTER_AUTH_ADMIN_USER_IDS`.

Partial or missing controls:

- The app has no formal tenant authorization layer, which is the principal blocker for school data isolation.
- Admin authorization is environment-managed static membership. Production access reviews, break-glass handling, and an immutable admin-audit trail are not evidenced in code.
- CSRF relies on Better Auth/same-origin cookie semantics and trusted origins; no separate application-wide CSRF middleware was found. Verify Better Auth’s deployed cookie and origin settings.
- Vercel/proxy configuration and database network/access controls are outside the repository and need direct review.
